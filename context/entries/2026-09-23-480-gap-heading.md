# 2026-09-23 — #480: a heading that claimed a prioritisation the table did not have

Branch `fix/480-gap-heading`, base `43bfa99`. `tier-1`, `client-reaching`.

## What was wrong

`attack/exporters.py`, DOCX and PDF paths:

```python
gap_rows.sort(key=lambda c: c.technique_code)
gap_rows = gap_rows[:50]
add_heading(doc, f"Top remediation gaps ({len(gap_rows)} of {ctx.rollup.gap} shown)")
add_table(doc, ["Code", "Technique"], rows)
```

**"Top"** — the sort key is `technique_code`. Alphabetical. The first fifty codes
win, and nothing about coverage, severity, tactic or effort enters the order.
**"remediation"** — two columns, `Code` and `Technique`, with no owner, effort,
control or next step.

`routes/attack.py` records a real run at 607 gaps, so a client could receive
"Top remediation gaps (50 of 607 shown)" over fifty alphabetically-first codes and
reasonably conclude those were the ones that mattered most. The parenthetical made
it worse by implying a selection had been made.

## The twins are deliberately left alone, and that is the checked answer

`csf/exporters.py` and `zt/exporters.py` carry the **same heading string**, so a
sweep by literal would have changed all three. They are not the same defect:

| service | sort key | table columns |
| --- | --- | --- |
| ATT&CK | `technique_code` — alphabetical | Code, Technique |
| CSF | `-priority_score`, then code | Code, Function, Subcategory, Current → Target, Priority |
| ZT | `-priority_score`, then code | Code, Pillar, Capability, Current → Target, Priority |

CSF and ZT genuinely rank, and their tables carry a target and a priority — "Top
remediation gaps" describes what is there. **ATT&CK ranks by nothing and offers no
remediation column, so it alone is wrong on both halves of its own heading.**

This is the fourth twin-sweep of the night and the first where the answer was
"leave them". Recorded in the code at the ATT&CK site, because a later sweeper
finding two files with the same string and one changed needs to know it was a
decision.

## What the new heading says that the old one hid

> Gap techniques, first 50 of 607 by technique code (alphabetical, not ranked; the
> Gaps tab of the XLSX carries all of them)

The order, the truncation, that it is an inventory rather than a plan, and **which
format truncates**. The XLSX `Gaps` tab builds from the same list with the same
sort and **no slice**, so the deliverable set does not withhold these rows — this
format does. Saying "50 of 607" without that sends a client looking for the
missing 557 in the wrong artifact.

## Scope

**The heading, and only the heading.** Ranked remediation is a large piece of work
designed separately and blocked on making long AI runs survive the browser. A
false claim in a client document does not wait for it.

## Verified

A test caught the change immediately — `test_the_gap_truncation_disclosure_is_actually_printed`
asserted the old string. That is the "changing copy breaks whatever asserts it"
rule working: the assertion **moved with the wording rather than being deleted**,
and was strengthened while it moved. It now pins three things where it pinned one:
both numbers, the words that make the order honest (`alphabetical, not ranked`),
and the absence of the old claim. A reword that kept the counts and dropped
"alphabetical" would have passed the original assertion.
