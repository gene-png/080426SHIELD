## Recurring defect shapes to watch for (CLAUDE.md)

A test that supplies its own expected value or precondition from the thing under test cannot fail — now 12 confirmed instances, this round's addition being `test_defect_3` in #103 (both fixture candidates shared a vendor, so deleting the rule under test left it green). A mechanism built to enforce a format only proves it handles the formats it was tested against — now two real instances: #98's self-audit catching the bold-`**Findings:**` case before shipping, and #103 catching the table-formatted Disposition case for real, in production, on the first complex PR to use the gate. Code can assert the opposite of what actually happens and nothing catches it until a human or an adversarial pass reads the code path directly — #103's panel-copy inversion (rejected citation read as "uncovered" when it actually read as fully covered) is the clearest instance of this shape logged so far; worth watching for elsewhere, since a wrong status message is arguably worse than a missing one. A fix that changes a value nothing reads is indistinguishable from a real fix by any test that only checks the value changed — #103's defect-1 finding (INCOMPLETE_VENDOR_DATA computed, never read) is the same shape as PR #97's no-op-guard bug, recurring in a different layer. A defect in one service or function exists in its twins until checked — unchanged from prior entries. A status line that is wrong is worse than none — unchanged from prior entries; #100 is this round's fix for the same failure mode DELIVERY_PLAN.md already had once. A mechanism that reports on a violation is not the same as a mechanism that blocks it — closed this round for the audit gate specifically, now that branch protection requires it; the general lesson stays worth watching elsewhere. Credential material never travels through a relay conversation, even when explicitly offered. Test behavior changes get called out explicitly in the test itself, never silently adjusted. A rule whose measured signal is a small fraction of its raw output should be narrowed rather than kept broad and ignored. A mutation-testing survivor is only meaningful relative to which tests were actually run against it. A migration's effect on existing rows is not uniform by default, and "old rows behave as before, new rows get the new behavior" has to be stated and tested as its own case.
