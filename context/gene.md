## The tool built to catch this class of defect had its own instance of it — PR #97

Same retro-audit, one layer down: #93's mutation-sweep tool matched AST nodes by (type, lineno, col_offset), which is not unique across chained calls sharing a position (e.g. update(X).where(...).values(...)) — every call in the chain reports the same position, ast.walk returns the outermost, and the tool silently mutated the wrong node. The resulting no-op mutant then gets reported as SURVIVED, sending a reader hunting for a missing test on a line that was never actually mutated. This shape exists in attack.py, csf.py, zt.py and tech_debt.py. The guard meant to catch a no-op mutant compared ast.unparse output against raw file text, which is never equal for any real file (comments and whitespace differ), so the guard could never fire. There was also no green baseline: any non-zero pytest exit counted as "killed," so a suite that never ran a single assertion due to a collection error would print "no surviving mutants" instead of surfacing the failure.

Also caught: the tool's finally-based restore does not survive SIGTERM, which is exactly what a cancelled GitHub Actions job sends, and the file it writes mid-mutation strips every comment via ast.unparse — meaning an interrupted run could have left a source file with every recorded reason-comment stripped, undetected. A .sweep-orig sidecar now makes that state detectable and recoverable. This exposure never materialized in practice: the nightly mutation-sweep workflow has never actually run (gh run list --workflow=mutation-sweep.yml returned empty).

Two more #72-pattern instances surfaced fixing this, both inside the tool built to find #72 instances: a test named for the no-op guard actually used input with no Call and no Compare node, so it passed for an unrelated reason before ever reaching the guard; and the new chained-call regression test itself initially passed for the wrong reason, counting two distinct mutant sources without checking that the real one was a genuine drop, not just a count. Both renamed and strengthened.

Do the previously-reported catch numbers change? No, and the reason matters more than the answer. The "5+2 real hits" figure is from the static checker (tier 1), which this bug never touched — re-measured, unchanged. The mutation sweep itself has produced exactly one real report ever, the #94 dogfood on tech_debt/exporters.py, a file with no chained calls, so the bug never actually fired there — re-run post-fix, identical, same 3 survivors. The nightly has never run at all. So nothing that already merged was validated by the broken tool; the numbers hold because the tool was barely used, not because the bug was harmless. On attack.py alone, the fix changed the no-op-mutant count from 8 to 0 — that is the exposure that would have hit the next real target, avoided by luck of timing rather than by any safeguard.

One more thing recorded rather than fixed: check_test_integrity's own blind-spot list was found incomplete (module-alias imports, a stringified needle bound on a prior line). Widening the rule to catch these was measured at 36 false positives against 2 real hits, so it was left narrow and the gap was documented instead — consistent with the standing principle that a rule whose signal is a small fraction of its raw output should stay narrow rather than get muted from noise.

## Recurring defect shapes to watch for (CLAUDE.md)

A test that supplies its own expected value or precondition from the thing under test cannot fail — 9 confirmed instances, plus one in #94's own test rewrite, plus two more this round inside the mutation-sweep tool itself (instance ten and eleven), both in tests written specifically to catch this pattern. A defect in one service or function exists in its twins until checked — the chained-call node-matching bug in #93's tool existed identically in attack.py, csf.py, zt.py and tech_debt.py. A false branch dropping a record silently instead of surfacing it under a different reason — three recorded instances, none new this round. A status line that is wrong is worse than none — DELIVERY_PLAN.md's own status table for items 3a and 4 still lags their actual merges. An empty collection being falsy is not the same as the collection being absent — this round's sharpest new instance: an approved list with zero security tools and an unapproved list both evaluated as "falsy," collapsing two states that needed to stay distinct, exactly the class of bug not x invites and a reviewer would suggest as a simplification. A green test suite proves nothing about a tool whose own baseline was never confirmed to be capable of failing — the mutation sweep's core defect, and worth generalizing: a tool that certifies other code's tests can fail needs its own tests to prove it can itself fail. Credential material never travels through a relay conversation, even when explicitly offered. Test behavior changes get called out explicitly in the test itself, never silently adjusted. A rule whose measured signal is a small fraction of its raw output should be narrowed rather than kept broad and ignored. A migration's effect on existing rows is not uniform by default, and a design that reads "old rows behave as before, new rows get the new behavior" has to be stated and tested as its own case, not assumed to fall out of the migration automatically.
